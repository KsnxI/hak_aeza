# Анализатор рисков оттока

Панель для маркетологов. Она показывает, каким клиентам платформы нужно внимание, почему у них растёт риск и сколько денег бизнес может потерять.

Для каждого клиента считается оценка риска (score от 0 до 100) с понятными причинами. Данные и коэффициенты можно менять, а результат обновляется сам, без перезагрузки страницы.

## Запуск

Нужен только Docker Desktop. Откройте терминал и выполните:

    git clone https://github.com/KsnxI/hak_aeza.git
    cd hak_aeza
    docker compose up --build

Первый запуск занимает несколько минут. Когда в консоли появится сообщение, что сервер запущен, откройте в браузере http://localhost:8000

Для входа используйте:

- Логин: admin
- Пароль: 451234780926

Если файла .env.development нет, создайте его из шаблона:

    cp .env.example .env.development

Чтобы остановить приложение, выполните docker compose down.

## Куда заходить

- Панель: http://localhost:8000
- Документация API (Swagger): http://localhost:8000/api/v1/docs
- Спецификация API: файл openapi.json в корне репозитория
- Метрики для Prometheus: http://localhost:8000/metrics

## Как проверить за 2 минуты

1. Войдите по логину и паролю. Без входа панель и API недоступны.
2. Откройте страницу Клиенты. Сверху карточки по уровням риска и сумма возможных потерь. Нажимайте на заголовки ID, Email, Баланс, Пополнено, Score: сортировка работает в обе стороны.
3. Откройте клиента с высоким риском. Вы увидите score, причины с вкладом каждого признака, его услуги и возможные потери.
4. Откройте страницу Настройки и подвигайте вес любого признака. Справа сразу пересчитаются количество клиентов по уровням и сумма потерь. Вернитесь в Клиенты: порядок строк изменился без перезагрузки. Закройте страницу и откройте снова: настройки сохранились.
5. В Настройках в блоке Источник данных загрузите другой JSON-снимок. Данные заменятся целиком, оценки и суммы пересчитаются.
6. Откройте страницу Дашборд. Там денежная оценка с пояснением и график оттока: сплошные линии это факт, пунктирные это прогноз.
7. Откройте адрес /metrics. Те же цифры (клиенты по уровням, сумма потерь) там отданы в формате Prometheus.

## Как работает модель

Для каждого клиента проверяются три признака. У каждого признака есть выраженность от 0 до 1 и вес.

- Услуга ожидает оплаты (prolong_wait), вес 45. Срабатывает, если у клиента есть услуга в статусе «Ожидает оплаты»: у неё остаётся 5 дней до удаления. Выраженность 1, если денег на оплату не хватает, и 0.6, если хватает.
- Не хватает средств (insufficient_balance), вес 35. Смотрим платежи ближайших 7 дней и считаем, какая их доля не покрыта деньгами клиента. Выраженность равна 1 минус средства, делённые на сумму платежей.
- Автопродление выключено (autoprolong_disabled), вес 20. Срабатывает, если у клиента есть действующая услуга с выключенным автопродлением, и срок её оплаты истекает в ближайшие 7 дней.

Формула: score равен 100, умноженному на сумму (вес × выраженность) и делённому на сумму всех весов. Результат округляется, получается число от 0 до 100.

Уровни риска: от 60 высокий, от 30 средний, ниже 30 низкий. Пороги можно менять в настройках.

Если у клиента нет услуг, оценка не считается, и панель явно показывает «Нет оценки».

Какие деньги клиента считаются: основной баланс плюс бонусный, если бонусы разрешено тратить (поле bonusState). Баланс для вывода (withdrawBalance) на услуги не тратится, поэтому не учитывается.

Почему выбраны именно эти признаки. Это три ситуации, на которые указывает задание: автопродление выключено при скором окончании услуги, на счёте не хватает денег на ближайшие продления, услуга находится в статусе prolong_wait. Самый большой вес у просроченной оплаты, потому что до удаления услуги остаётся всего 5 дней. Дальше идёт нехватка денег и затем выключенное автопродление.

## Как считаются деньги

- Цена каждой услуги приводится к месячной: час умножается на 720, неделя на 4.3, месяц на 1, квартал делится на 3, полгода на 6, год на 12.
- Возможные потери по клиенту равны score, делённому на 100 и умноженному на месячную стоимость его действующих услуг. Действующие это услуги в статусах active, suspended и prolong_wait. Удалённые и заблокированные не считаются.
- Потери бизнеса это сумма потерь по всем клиентам.
- Баланс клиента влияет на оценку через признак «Не хватает средств»: чем лучше покрыты продления, тем меньше score и потери.
- В данных суммы лежат в «евро-копейках»: 100 единиц это 1 евро. Интерфейс показывает евро.

## Как устроено

- Данные загружаются JSON-снимком (PUT /api/v1/source/snapshot) и сохраняются в базу PostgreSQL: клиенты, услуги, транзакции, настройки модели, сессии.
- Бэкенд на Python (FastAPI) считает score и деньги, отдаёт данные панели, метрики Prometheus и поток событий для живого обновления.
- Панель написана на React и TypeScript (Vite, Tailwind, React Router, TanStack Query, Recharts). В Docker она собирается внутри образа и раздаётся тем же сервером, что и API.
- Вход по логину и паролю, сессия ограничена по времени. Данные клиентов и настройки без входа недоступны.
- Живое обновление: после изменения данных или коэффициентов сервер отправляет событие (SSE), панель перезапрашивает данные и перерисовывается сама. Настройки хранятся в базе и переживают перезапуск.
- Миграции базы делает Alembic. Запуск целиком через Docker Compose.

## API

Документация и возможность попробовать запросы: /api/v1/docs

- POST /api/v1/auth/login: вход по логину и паролю
- GET /api/v1/auth/me: текущий пользователь
- POST /api/v1/auth/logout: выход
- GET /api/v1/customers: список клиентов с оценкой риска, поиск, фильтр по уровню, сортировка, страницы
- GET /api/v1/customers/{id}: подробная оценка клиента, услуги, признаки и объяснения
- GET /api/v1/analytics/summary: сводка по риску, денежная оценка, данные для графика
- GET /api/v1/model/settings: текущие коэффициенты и пороги
- PATCH /api/v1/model/settings: изменить коэффициенты, результаты пересчитываются
- PUT /api/v1/source/snapshot: загрузить или полностью заменить снимок данных
- GET /api/v1/events: поток событий для живого обновления
- GET /metrics: метрики Prometheus

Метрики: churn_customers с меткой level (high, medium, low, none), churn_potential_loss_units, churn_potential_loss_eur, churn_services_at_risk. Значения берутся из того же расчёта, что и сводка в панели, поэтому цифры совпадают.

## Как добавить новый признак

1. Создайте файл в папке backend/features, например backend/features/large_topup_gap.py:

        from backend.features.registry import feature

        @feature("large_topup_gap", label="Давно не пополнял баланс", default_weight=10)
        def large_topup_gap(customer, services, settings):
            # вернуть выраженность от 0 до 1 и текстовую причину
            if customer.days_since_last_topup > 60:
                return 1.0, "Больше 60 дней без пополнения"
            return 0.0, "Пополнения регулярные"

2. Перезапустите сервер: docker compose up --build

Признак сам появится в расчёте score, в причинах клиента, в настройках (со своим слайдером веса) и в метриках. Миграции базы не нужны, потому что веса хранятся в одном JSON-поле.

## Разработка без Docker

Бэкенд, из корня репозитория:

    cd backend
    python3 -m venv .venv
    source .venv/bin/activate
    pip install -r requirements.txt
    cd ..
    uvicorn backend.main:app --reload --port 8000

Фронтенд, в другом окне терминала:

    cd frontend
    npm install
    npm run dev

Панель откроется на http://localhost:5173, запросы к /api пойдут на порт 8000.

Чтобы запустить панель без бэкенда, создайте файл frontend/.env.development.local со строкой VITE_USE_MOCK=true. Тогда данные генерируются в браузере, а для входа подходят логин admin и пароль admin.

## Что где лежит

- backend: сервер, маршруты, модели, миграции, расчёт риска и признаки
- frontend: панель на React
- data: тестовые данные (положите сюда файл снимка)
- openapi.json: спецификация API
- Dockerfile, docker-compose.yml, .env.example: запуск и настройки

## Допущения

- В тестовых данных нет истории статусов и дат удаления. Поэтому «факт» на графике накапливается с момента загрузки данных, а «прогноз» считается по датам окончания услуг с выключенным автопродлением.
- Названия некоторых полей в источнике с опечатками (pice, paymentTem, pefomed). Они приводятся к нормальным именам при загрузке снимка.
